# 羊TOKEN中转站更新流程

## 功能开发与自动验证

1. 在功能分支上开发，不直接改生产服务器。
2. 推送分支或创建 PR 后，GitHub Actions 自动并行执行后端单元/集成测试、Go lint、前端 lint/类型检查/全量测试/生产构建，以及 Linux amd64 Docker 镜像构建。
3. Docker Buildx 使用 GitHub Actions 缓存；相同依赖层可复用，减少重复下载与编译。
4. 检查全部 CI job 通过后再合并。CI 只验证代码和构建镜像，不会连接或修改生产机。

## 生产发布

- 生产发布仍由管理员单独发起；普通分支推送、PR 合并和 CI 镜像构建都不会部署生产。
- 发布前确认目标为管理员指定的生产主机及 `linux/amd64` 架构，确认数据库备份可恢复、保留旧镜像/Compose 回滚点，并核对健康检查与关键页面。
- 涉及数据库迁移、计费、余额、支付或请求路由时，除 CI 外还要先用隔离数据库演练迁移；不能仅因 CI 通过就跳过生产备份和人工发布确认。
- 发布后检查容器健康、版本、`/health`、用户/管理入口及错误日志。普通应用回滚只恢复旧 Compose 镜像配置，不覆盖升级后新增的生产数据；只有确认数据损坏时才考虑恢复数据库备份。

## 常用验证入口

- 自动流程：推送功能分支或 PR，查看 Actions 中 `CI` 的全部 job。
- 本地快速检查：`make test-frontend`（关键前端用例、lint 和类型检查）；后端可运行 `make -C backend test`。
- 完整前端回归：在 `frontend/` 执行 `pnpm run test:run`，再执行 `pnpm run build`。
